# 报告审核后续动作：尚未实现的安全恢复设计

状态：设计待实施，不能作为验收通过证据。仅功能分支，本地隔离实施，不改变生产Mongo架构。

03:15进展：旧复查路径已实现来源原子占用和写/删保护，输入随领取保存；发生异常保留running，工作台投影超时。尚不是审核同文档pending意图，也没有目标epoch和安全恢复；条件草稿仍未覆盖。以下其余设计不可视为已实施。

## 已确认问题

- 固定Review/Task ID可防重，但不能使旧审核快照失效。legacyReviewStaleSource真实Mongo在写Review前、写Task前撤销来源，两场景均仍建Task。
- report.save成功后、后续动作前硬退出会漏派；Review成功Task失败只有显式重试，没有自动恢复或工作台异常。
- 条件草稿涉及HealthPlan内容更新，不能只给旧Task加锁就声称所有后续动作安全。

## 实施顺序与约束

1. 审核同文档保存显式后续动作意图：冻结审核人员、客户、输入、来源版本与token。首次意图必须CAS；旧请求不能覆盖新版本。重复提交读取原意图，不能重置completed。历史报告不自动回填。
2. 执行者原子领取pending→running，并与现有planItemSync运行占用互斥。所有报告save/更新/删除保护须同时考虑两种占用；内部绕过能力仍不接受客户端参数。运行占用未解除时禁止改审核/关联/来源客户。
3. Review、Task和条件方案各需持久版本屏障。固定ID仅解决重复，不解决旧执行者。Task/Review首次插入、条件方案更新必须带当前epoch条件；恢复前先让所有旧目标写失效，再释放来源。新目标尚不存在时的屏障也必须预先建立，不能只在已存在记录上加条件。
4. 不采用仅超时解锁：无法证明目标屏障成功时保持锁定并在所属人员工作台展示异常。不得以“任务已生成”代替全部目标的完成回执，也不因时间久就覆盖已完成/取消Task。
5. 复用每日扫描，先扫描显式新pending意图；安全恢复未完成前不接管running。条件模块草稿须保护人工已决定结果，不能用整个旧content快照覆盖其他人修改。
6. 回执与占用版本CAS；完成后撤销审核不静默删除已执行服务，须独立有审计的纠错流程。任务责任人来自冻结凭据，人员调岗不以重试时登录者替代。

## 必须通过的隔离验收

- 审核保存失败零后续副作用；保存后进程退出能从持久意图恢复。
- Review前/Task前撤销来源：撤销被占用保护拒绝，或旧写完全失效；不得出现成功撤销后新建任务。
- 半成功、回执丢失、旧进程仍活着、恢复屏障失败、双扫描器并发；原完成时间/人工决定不重写。
- 真实HTTP重复/并发、权限与归属；所属岗位工作台异常可见，恢复后只移除对应异常。
- 不以单测、模拟AI或这个设计文档宣称完整闭环。现有失败数据保留。
