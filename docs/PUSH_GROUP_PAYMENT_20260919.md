# 推送多商品一次微信支付（2026-09-19）

## 用户确认与基线

用户明确选择“勾选多件，合并一次微信支付”。基于 `e961b5b9`（含营养实物付款话术、实收金额积分修复），不回退旧代码。上次小程序开发上传版本为 1.0.168；本次计划上传 1.0.169。开发上传不等于审核/正式发布。

## 业务与安全边界

- 推荐弹窗默认全选，支持独立勾选、取消全选/恢复全选。提交中锁定选择和连点；订单创建后转“我的订单”继续付款或取消，不重复创建。
- 多件仍各生成一个商品订单，保留各自推送人、服务人、健康规划师、商品工作流和履约快照。一张 `Payment.allocations` 记录各订单实付，只发起一次 JSAPI 收款。历史单件 Payment 兼容。
- 优惠券按商品金额分摊；自有基金优先，企业基金按各商品允许范围/限额分配，全部使用整数分核算。每项标价 = 优惠券 + 自有基金 + 企业基金 + 微信实付，各项实付之和等于微信收款。
- 服务端报价与页面合计不同，先显示重新核算后的金额，再次点击确认才下单。6800 + 318.44 = 7118.44，实际可抵扣 68 时微信收款 7050.44。
- 消费积分只按实际现金支付计算；合并款按总实付取整后分配到各商品，避免逐件舍入额外损失积分。退款撤回该商品积分。历史余额不迁移/重算。
- 回调逐件确认，数据库租约串行化同笔合并收款的回调，防并发重复扣基金/奖励。支付事实先写，副作用失败可由状态查询重试。全部子订单确认前，小程序不显示整组成功。
- 原支付关闭成功后才允许重新发起。从任何子订单继续支付都使用整组总额。取消待付合并单会关闭整组，前后台均明确提示；已付款商品只能申请退款。
- 退款上限为单件剩余实付，微信退款 `total` 仍为原合并收款总额；实付 0 的子项仅退内部权益。共用券全部子项退款后才恢复，迟到的支付回调不能复活已退子项。
- 逐项验证上架、支付通道、负责人和库存。第二件失败时补偿第一件；网关超时不是未支付证据，保留整组及库存等待查单。
- 微信履约上报读取共用 Payment；所有未退款子项均具备配送/服务证据后才上报该笔完整交付，含各实物包裹。内部子项履约记录不受影响。
- 每次最多 10 件不同商品。不新增多商户合单接口、不改支付密钥、不代用户实际扣款、不改历史订单。

微信普通商户退款口径参考：[申请退款](https://pay.wechatpay.cn/doc/v3/merchant/4013071036)。这里是一张普通 JSAPI 商户付款单，不是跨商户“合单支付”接口。

## 双端评估

App/网页推荐页未接小程序 `requestPayment`，继续受既有 `wechat_jsapi_v1` 能力门槛保护。本次仅小程序开放合并付款；共享订单 API、Admin 退款/取消及履约已兼容。不能把网页多选 UI 描述为已支持网页微信合并付款。

真机验收：原两商品推送 → 分别勾选/全选 → 核对合计 → 微信仅弹一次付款 → 取消后从第二件订单继续支付 → 成功后两项分别已付款。真实收款/退款由用户按业务需要操作，自动化测试不等于真机资金验收。
