# 年度体检提前准备：分步实现

## 当前边界（2026-09-19）

已完成准备窗口及双岗位候选的确定性计算、旧每日扫描误改派修复、已存在准备任务的工作台办理和结果回写、独立标准模板草稿、后台AI加项队列、顾问审核写回，以及双岗位当前证据的只读汇合校验。**尚未接入年度确认/每日派发；实际服务选择关联及预约承接仍未完成，不表示已经自动生成两岗位准备任务。** 未部署、不迁移历史任务，不创建体检订单；新建标准草稿自动进入加项准备，旧草稿保持原显式生成方式。

`annualCheckupPreparation.js` 是纯计算模块，输入年度方案、客户、`annualPeriodicGate` 的完整结果和当前时间。返回 `state`、任务候选、阻塞原因；本身不读写数据库。`tasks` 不是已派发记录，`issues` 也还没有投递至岗位工作台。

## 已验证的准备规则

- 按北京时间，以体检日前14天进入窗口；此前不铺设任务。
- 准备起点不得早于客户确认、有效执行起点、当前可信服务期开始。确认较晚或续年起点较晚，立即准备并标记不足14天。
- 两个并行候选：所属健康顾问准备并审核体检方案；所属健康规划师沟通时间和体检资源。无互相前置依赖、不转给健管专员、不生成客户打卡任务。
- 两岗位都适用于体检模块，不依赖是否购买就医协助；实际服务仍沿原授权和订单流程。
- 缺少岗位时返回明确问题，不用创建人或健管专员冒充；另一有归属的岗位仍有候选。
- 日期必须明确、有效且在服务期内。已过体检日期不补发新预约任务，返回顾问核对事项；当天可准备。
- 改期采用已有有效日期覆盖层，任务键仍取冻结原日期，纳入既有改期影响检查。不修改冻结方案。
- 候选身份和排期不随每日扫描漂移。但**数据库唯一派发与失败恢复尚未接入**，不能以候选稳定等同真实数据库幂等验收。

## 已接入的旧逻辑修复

原每日扫描仅凭标题包含“就医提醒/年度体检”就把任务改派给健管专员，会影响同名顾问、规划师和服务流程任务。

现在只校正带年度来源的 `scheduled` 普通提醒，且尚未开始、无岗位流程标识、无服务/订单来源、无服务关联且未阻塞。写回还检查原负责人、状态及上述来源条件，避免读取后已经完成、人工改派或关联服务的记录被迟到更新覆盖。没有批量修复以前可能已误改的历史数据，历史归属需另行只读核查。

## 工作台办理与完成证据（已接代码，未启用派单）

入口复用员工端现有服务任务卡片→客户随访详情，显示 `AnnualCheckupPreparationCard`；没有新增客户任务或新的定时器。

- 顾问选择本客户、本年度方案确认后建立的有效体检方案；可先关联草稿。该操作只保存关联证据，不创建方案或服务。选择记录保留操作者和时间，重新选择保留历史。
- 草稿关联后，原方案实际审核发布（有审核人和时间）才自动完成准备；仅写 `approved`、仅发布或仅草稿不能冒充完成。原方案保存/单ID更新触发精确来源回写，工作台读取及现有每日扫描兜底。已完成历史不重开。
- 规划师记录同一目标日、体检机构及客户/机构双方实际沟通结果；保存即完成本岗位准备，不额外点击“完成”。不在此处修改年度排期，也不把资源可行当成正式预约。
- 专用接口限定任务岗位和负责人；超管可代办。通用随访修改、审核和删除不能绕过专用证据。写回比较原状态、负责人、时间版本及原证据，避免同一毫秒内的并发覆盖。重复保存已完成记录返回409，刷新查看原结果，不重开或重复写入。
- 通用年度服务需求清理排除准备流程，避免把独立准备任务误取消。既有订单写入不新增体检扫描；体检方案写入只检查明确关联该方案的准备任务。
- API：`GET/PUT /api/staff/followups/:id/checkup-preparation`。这里只办理已存在的准备记录，**接口不能创建准备任务**。

完成回写不是两岗位条件汇合或预约解锁。后续汇合还必须重新核验方案/资源的当前有效状态；不能仅凭历史 `completed` 直接启动服务。当前未做通用退回重办，未更改已运行体检服务。

## 独立标准草稿入口批次

- `POST /api/staff/followups/:id/checkup-preparation/draft`：仅本准备任务的健康顾问或超管可操作，同时受随访编辑、方案创建和体检方案类型权限限制。
- 选择当前平台有效模板，原样保留标准项目和可选加项库；生成待审标准草稿，带年度来源及目标日期。没有自动AI选加项、没有推送、没有自动审批、没有订单或 `medical_assist` 服务实例。原方案页面的编辑/审核/讨论仍可使用。
- 建立后自动关联准备任务；同任务的草稿 ID 确定性派生，依靠 MongoDB `_id` 固有唯一约束，重试仅恢复关联，不覆盖草稿编辑。不是多文档事务：草稿成功、任务关联冲突时返回409并保留草稿；任务仍有效时刷新重试复用同一份。若任务已关闭或改派，草稿保留待核对，不自动发布/启动。
- `HealthPlan.preparationTaskId` 为独立不可变来源标记，通用内容编辑无法移除。准备方案不可直接硬删除后重建，可修改或取消；取消后的同任务自动重建尚未支持，不能自动复活。
- 客户只能确认已审核发布的准备方案；确认只记录方案确认，不启动体检服务。旧 `onCustomerConfirmedCheckupPlan` 对准备来源直接返回，防止无 `serviceInstanceId` 时回退到最近旧服务；报告回传和旧生成器的候选亦排除准备来源。
- 这是一项明确隔离措施，**不是后续承接已经实现**。正式启用前必须增加双岗位当前证据汇合和显式服务实例关联，再有条件放行预约；不能简单去掉准备来源的阻断。

新增13项草稿、权限、失败恢复、客户确认及旧服务隔离测试，相关回归共461项通过（460项主回归及1项会话排序补跑）。员工端构建通过，仍有既有大包警告。未使用真实数据库或浏览器多岗位验收，未部署。

## AI加项输入/输出校验基础批次（尚未接业务入口）

`checkupPreparationAddons.js` 为独立计算模块，提供资料快照、受限模型调用和结果校验；不读写数据库，不修改项目，不创建任务/服务，不自动审核。新建准备草稿仍仅复制模板。

- 只接受同客户、同平台的未发布待审准备草稿。标准项目及已有项目按名称排除，候选仅来自草稿保存的模板加项库；AI只能返回索引，项目名称和标识由系统映射。
- 评估须同客户、已批准、有顾问审核凭据、处于有效期且未被替代；报告须同客户且整份已审核。保留评估依据、检查建议及完整报告项目文字；档案仅作背景，去除姓名/电话及非必要档案字段。
- 每项建议必须附理由和合法来源引用；严格JSON解析，拒绝未知字段、越界、重复项目、重复/虚构来源及不完整输出。**来源存在性不等于医学语义正确**，顾问仍需核对理由与原始资料。
- 输入保留方案时间版本、模板版本、报告审核修订、评估信息及内容指纹。上限40,000字符，超限明确失败，不悄悄截断医学结论。没有可选项目或有效审核来源时跳过，不消耗模型调用。
- 调用函数由调用方注入；限定一次、2,000输出token、45秒超时，失败直接上抛，不自行重试或降级造结果。后续业务接入必须注入现有受预算控制的 `ai.chat`，补权限、持久排队/运行标识、进程中断恢复及保存时重新校验当前来源和方案版本；指纹本身不是数据库并发锁。
- 尚未接API、页面、持久队列或顾问采纳写回；不应直接从读取页面/每日扫描调用模型。不得覆盖顾问编辑或已发布方案，不得解除准备方案与旧服务的隔离。

新增12项纯模块测试，相关回归共473项通过。无前端改动，未重新构建；未调用真实AI、未进行真实数据库/浏览器验证，未部署。

## AI加项持久生成及审核入口批次

已接 `CheckupPreparationSuggestion`、`checkupPreparationSuggestion.js` 及独立准备方案页面组件。仅本任务顾问或超管可办理，叠加原随访/方案模块及体检方案类型权限；不是所有方案编辑者均能读取此评估快照。

- `GET/POST /api/staff/followups/:id/checkup-preparation/addons` 读取/显式生成；`POST .../addons/review` 审核所选加项；`POST .../addons/recover` 仅超管确认旧请求已停止并填写原因后恢复。
- 独立员工端集合以方案 `_id` 为唯一身份，生成前持久占用；并发首建依靠数据库固有 `_id` 唯一约束，重试比较原token/状态。已在运行的不抢占、不因超时自动重跑。同输入成功结果复用，失败或来源更新可显式重试并保留历史尝试。
- 通过现有 `ai.chat` 和预算上下文调用，每次最多一次模型请求。不在页面读取或扫描中调用AI；失败保存通用提示，不将提供方原始报错或资料写入错误消息。
- 临床来源快照存独立集合，不放入客户方案；生成只写建议、不更改项目。审核前重新读取有效来源并比对指纹；人工核对引用后勾选，可全部不采纳。所选项目与审核证明在方案同文档一次保存，比较原方案时间、内容、项目和未审核标记，避免覆盖并发编辑或重试重复加项。
- 加项审核不等于整份方案审核：方案仍为待审草稿，沿原审核发布入口。不创建订单/服务、不推送、不改客户确认行为，准备来源与旧服务隔离保持不变。
- 运行中断必须人工核实；管理员恢复后，旧运行token/状态保护阻止迟到结果写回。若保存生成结果时数据库不可用，可能保留 `running`，不能自行假定模型未执行或自动重试。
- 新记录依据读取时来源版本做校验，**不是多文档事务快照**；资料在核验后瞬间发生跨集合变更仍需后续一致性验收。整体沿用原方案编辑行为，不能宣称已解决全系统多页面编辑竞争。

当前仍需点击生成及审核，并非自动入队执行。后续应接准备草稿创建后的持久入队与中断恢复，让通常流程免去“生成”操作；不得仅用无持久记录的后台promise替代队列。双岗证据汇合、正式服务显式关联和自动任务派发仍未接。

新增16项服务状态测试及3项HTTP路由测试，相关回归492项通过；员工端构建通过，保留既有大包警告。使用模拟数据库和本地HTTP，未调用真实AI、未做真实MongoDB并发或浏览器多岗位验收，未部署。

## 新建准备草稿自动队列批次

- 新草稿初次写入时同时写入不可变 `preparationAddonAuto: true`，作为持久待处理意图；不靠HTTP之后的临时promise记住待办，不回填旧草稿。任务关联成功才入 `queued`，草稿建立但关联失败时不消耗AI，修复关联后恢复。
- 新建接口只唤醒后台，不等待模型；复用既有年度窗口启动扫描和每天一次扫描兜底，无新高频定时器。扫描数据库本身不消耗token，只有尚未生成的有效准备任务可能调用AI。
- 先按方案固有唯一_id插入队列，再由原生成服务比较token/状态抢占，自动与手动请求竞争仍只允许一个请求调用模型。已成功/跳过/失败/运行中的记录不重新自动生成；运行中断沿用管理员确认恢复，失败显式重试。
- 用游标遍历新草稿意图及排队记录，不限制只处理首25/500条。当前每进程串行生成；跨进程靠单方案原子占用避免同方案重复，不是全局并发限流器。预算仍由现有AI控制统一限制。
- 执行前重新读取员工、在岗状态、自定义权限与机构归属；后台不继承唤醒请求的租户上下文。原服务再核验任务归属/方案状态/来源。缺权限、改派、资料异常等失败留在原准备方案中，不增加客户任务或另发“点击完成”待办。
- 页面在排队/运行时短时读取状态（最多20次，每3秒一次），读取不调用AI；离开页面停止。顾问通常只核对建议并审核，人工重试仅处理异常。普通用户不会看到员工队列的资料快照。

新增7项队列测试及1项自动/手动竞争测试，相关回归500项通过；员工端构建通过，仍有原有大包警告。模拟数据库/本地HTTP验证，未调用真实AI或真实MongoDB，未做浏览器多岗位验收，未部署。双岗位结果汇合、显式服务承接及自动准备任务派发依然未完成。

## 双岗位当前证据只读汇合批次

`checkupPreparationReadiness.js` + `GET /api/staff/followups/:id/checkup-preparation/readiness` 接入原准备卡片。仅本任务岗位人员或超管读取，读取后再次核对归属；没有新增人工确认按钮或客户任务，不调用AI、不写数据库。

- 使用现有 `annualPeriodicGate` 和有效排期投影；服务期失效、尚未进入窗口、过期体检、缺岗等不放行。按同客户、年度及冻结排期键配对，不用标题/最近任务猜测；重复记录、错配、改派、锁定、取消、完成凭据缺失均阻止就绪。
- 顾问任务历史完成仍需复核当前独立准备方案的归属、审核人/时间、有效发布及目标日。旧无准备来源的体检方案不借此解锁新路径；原流程保持不变。
- 客户必须确认本次已发布版本，确认时间不能早于最近发布或晚于当前时间；未确认显示规划师待沟通，不另铺客户打卡任务。
- 规划师任务完成还必须具有同目标日、机构、沟通说明、双方确认、记录人和有效记录时间；日期变更不能沿用旧日期凭据。
- 所有条件满足只返回 `ready_for_service_link`，表示具备进一步选择/核验现有服务的准备条件。`serviceStarted: false` 表示本接口没有启动服务，不表示客户不存在其他进行中服务。
