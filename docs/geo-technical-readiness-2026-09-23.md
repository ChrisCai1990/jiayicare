# GEO 技术承载盘点与建设方案

## 当前结论

现有 App Web 部署使用单页应用重写规则：任意路径均返回同一个 `index.html`。代码中未发现独立的 `robots.txt`、`sitemap.xml`、公开知识内容路由或每页独立的标题/描述配置。

这适合登录后的健康管理系统，不适合承载 GEO 的公开内容资产。搜索和 AI 引用需要稳定、可公开访问、可识别主题与来源的独立 URL；不能把内容只放在登录后 App、小程序或单页 JavaScript 界面里。

## 推荐架构

```text
公开知识中心
  - 专题支柱页
  - 单问题内容页
  - 服务边界和团队事实页
  - robots.txt 和 sitemap.xml
  - 作者/审核/更新时间/引用信息
        |
        v
测评落地页
  - 明确授权
  - 风险分流
  - 可追踪来源
        |
        v
现有小程序 App 和后台
  - 登录与建档
  - 健康管理师承接
  - 预约和成交归因
```

## 首版知识中心范围

| 页面类型 | 首版数量 | 必需元素 |
| --- | ---: | --- |
| 体重与代谢专题页 | 1 | 服务边界、问题导航、风险提示、测评入口 |
| 高意图问题页 | 20 | 单问题答案、审核信息、参考依据、唯一行动入口 |
| 服务说明页 | 1 | 适用人群、流程、非医疗边界、预约方式 |
| 团队与审核页 | 1 | 真实公开身份、职责、审核机制 |
| 隐私与测评授权页 | 1 | 字段、用途、授权、保存和联系人 |
| 站点技术页 | 2 | `robots.txt`、`sitemap.xml` |

## 技术要求

- 每个内容页面有独立、永久、可读的 URL，例如 `/guides/metabolic/fasting-glucose-next-steps/`。
- 页面应在初始 HTML 中包含标题、描述、正文、作者/审核人和更新时间，而非完全依赖登录后客户端渲染。
- 生成 `sitemap.xml`，只列入允许公开索引且已审核的页面；为站点根目录提供 `robots.txt`。
- 使用 canonical URL；不要为同一内容制造参数重复页。
- 统一标记来源参数：`utm_source`、`utm_medium`、`utm_campaign`、`topic_id`，并在测评侧写入 `first_source` 和 `landing_topic`。
- 不把用户健康数据放入 URL、前端埋点参数、公开页面或第三方分析工具。

## 内容发布门禁

1. 内容负责人确认事实、服务范围、审核人和发布日期。
2. 专业审核人确认健康表述、风险提示和就医边界。
3. 运营审核人确认没有疗效承诺、未授权案例或违规导流。
4. 技术检查确认 URL、canonical、站点地图、页面加载和测评归因可用。
5. 每周以固定问题集抽检 AI/搜索回答；发现品牌或事实错误时先更新权威页面，再记录纠偏结果。

## 发布前需要确认但当前不阻塞开发的事项

- 公开知识中心使用的正式域名或子域名。
- 可对外公开的机构主体、城市/服务范围、团队资料和联系方式。
- 内容审核人及其能公开展示的姓名/身份。
- 测评落地后进入小程序、App、H5 或人工预约页的最终路径。

在上述信息明确前，可以完成站点模板、信息架构、首批内容草稿、站点地图生成和测评数据结构；不得对外发布。
