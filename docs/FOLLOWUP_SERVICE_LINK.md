# 管理随访与实际服务关联

本次实现属于功能分支，尚未生产部署。它补齐“服务需求 → 关联既有服务 → 原随访自动回写”，不代表病历/报告自动生成新随访等全部闭环已完成。

## 使用与岗位

健康规划师打开工作台服务需求，在详情中选择对应健管随访及同一客户已建立的有效服务订单/服务方案。动态评估来源自动限定为原随访；年度来源限定为同一年度方案的已审核随访，由规划师确认对应事项。缺少随访或可用服务时，先按既有流程建立，不伪造订单、付款或服务启动。

每条需求/随访只保留一个关联记录。进行中的关联不可替换；异常交回人工后，规划师可重新选择有效服务，保留替换历史和版本号。服务关联不改变原订单或方案的岗位、步骤和验收要求。

## 状态

- 进行中：需求及随访为只读进度；健管工作台显示折叠进度，不计入待随访数量。原服务工作流按当前岗位继续办理。
- 完成：以原服务 `status=completed` 为准，自动完成需求和随访；多次服务订单必须全部核销，不以单次核销视为整单完成。
- 取消、退款、执行异常或关联记录缺失：需求和随访回到 planned，解除阻塞并提醒跟进。退款失败不等于服务失败。
- 异常交回人工后，旧服务的后续变化不再自行关闭随访；需人工解决或关联新的有效服务。

关联进度按版本单调回写，重复核验不反复刷新完成时间，也不覆盖人工已处理的异常任务。通用编辑和客户自主完成不能跳过进行中的服务，进行中也不可删除关联随访。

## 同步与兼容

订单及服务方案 save/findOneAndUpdate/单ID updateOne 后触发只针对关联事项的状态核验。同步失败记录日志，不使原有服务保存失败；在工作台、客户随访详情读取时补偿，并复用原每日扫描兜底。批量更新或原生driver更新通过读取/每日核验补偿。没有新增高频扫描，也没有AI调用。

新增 `FollowUpServiceLink` 集合，需求ID和随访ID分别唯一。`FollowUp.serviceTracking` 仅为服务状态展示投影，通用编辑接口不接受写入。没有关联的历史流程不产生新的管理随访；不批量迁移历史数据。

上线前核验新集合唯一索引已建立，并在测试数据库检查：成功完成、多次核销、取消、退款、异常重选服务、重复提交、回写中断后重试，以及各岗位可见性。

## 验证范围与剩余项

自动测试覆盖状态判断、部分核销保护、异常交回、旧版本回写保护，以及真实HTTP路由下的岗位授权、同客户限定、重复绑定和有效关联。数据库访问使用模型替身；真实MongoDB并发/唯一索引和浏览器分岗位验收仍需执行。

当前关联的是完整服务订单或独立服务方案，不支持把多次订单中的某一次核销单独绑定到一条随访。病历/报告自动触发新随访、跨来源建议合并、阶段性评估和年度总评仍按总体方案继续实施。
