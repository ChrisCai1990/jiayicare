# 健康顾问主线与统一工作台现状审计

审计日期：2026-09-05

审计范围：`staff/`、`backend/`、`admin/`、用户端相关 API；本轮仅审计，不改业务代码。
目标口径：客户详情页回答“客户走到哪一步”；角色首页回答“我现在要做什么”；AI 医学内容审核通过前不得展示、入正式档案或触发下游任务。

## 结论摘要

当前系统不是从零开始：角色归属字段、随访任务、AI 待审聚合、逾期三次升级、三类方案模板和部分自动归档都已存在。但“统一工作台”仍是多个独立面板的拼接，缺少统一任务模型、统一统计口径和状态闭环。

优先级最高的两个现存问题：

1. 医护首页调用 `staffAPI.getReports()`，该方法实际请求 `/staff/medical-reports`；真正的首页简报是 `getReports2()` → `/staff/reports`。因此“我的会员、今日随访、本月随访、慢病分布”没有使用简报数据源。
2. 年度管理方案在保存时即调用 `syncAnnualPlanFollowUps`、`syncAnnualPlanSupplyPlans` 和 `syncAnnualPlanTreatments`，早于推送/客户确认，也没有独立 AI 审核状态，违反“审核前不得生成正式执行任务或触发下游派单”。

## 一、统一工作台与统计

| 能力 | 状态 | 现状证据 | 差异/风险 | 建议验收口径 |
|---|---|---|---|---|
| 我的会员 | 需修改 | `/staff/reports` 已按角色对应 `assignedXxx` 统计，并支持团队可见人员；首页却误调体检报告列表 API | 首页数值可能为空；“有效会员”未限制会员有效期、停用/软删除状态；团队范围也不等于“本人实际负责” | 当前人员对应归属字段、人员有效、会员未删除且服务有效；团队统计另设入口，不混入“我的会员” |
| 今日随访 | 需修改 | 后端按 `date` 在今日范围内统计所有状态 | 未区分待/已；取消也可能计入；已完成应按 `completedAt`，不是计划日期 | 同卡显示“待 N｜已 N”；待按计划日和开放状态，已按实际完成日 |
| 本月随访 | 需修改 | 后端按 `date` 在本月统计所有状态 | 已完成跨月执行会错算；上月逾期在本月工作台可能不进入本月数 | 待按计划日期；已按 `completedAt`；逾期独立且跨月保留 |
| 逾期随访 | 部分具备 | `overdueFollowUpScheduler` 已实现到期次日提醒、隔日提醒、最多 3 次，第 3 次置 `overdueEscalationStatus=pending`；完成时可解除 | 首页普通随访面板仅拉 `planned`，遗漏 `in_progress/missed`；逾期升级混在“AI待审核任务”，术语和职责不准确；没有独立逾期总入口 | 所有开放状态纳入；“逾期/督办”独立区；完成或取消后自动从升级区消失 |
| AI 待审核 | 部分具备 | `/staff/ai-todos` 已按角色与客户归属聚合大量类型，并按优先级/超时排序 | UI 是独立 `AiTodosPanel`；类型映射仍含历史职责，例如年度体检待审归健管专员，与最新业务口径冲突；不是统一任务状态机 | 每种医学 AI 内容只有一个明确审核角色；审核前无客户端可见、无正式任务、无正式档案写入 |
| 待随访 | 部分具备 | `FollowUpsPanel` 展示计划中任务并排除订单预约 | 只查 `planned`；`in_progress/missed` 未显示；健康顾问默认可看到名下客户所有执行人任务，容易把“督办”与“本人执行”混成一个列表 | 首页默认只显示本人主责执行任务；对名下客户的质量监督作为关联督办任务 |
| 订单预约 | 部分具备 | 首页单列 `sourceType=order` 且 `scope=assigned` | 与工作台其他任务分面板展示，无统一紧急度、期限和状态；无负责人时静默不建任务 | 无负责人必须进入异常队列；统一展示并保留“服务预约”类型 |
| 角色专项任务 | 部分具备 | 报告解析、体检进度、客户到期、消息、不适主诉等已有独立面板 | 首页持续纵向堆叠，不能统一排序、筛选和去重；同一业务可能同时出现 AI 审核、随访和专项卡 | 汇总为统一任务列表，支持类型、紧急度、期限、主责/督办筛选 |
| 客户全周期进程 | 部分具备 | 客户详情已有方案、随访、服务记录和审核工作台信息 | 目前主要是多个 Tab/数据区，并非单一、可追踪的全周期状态；方案/任务/服务记录之间的状态更新不完整 | 客户详情形成只读进程时间线，来源可追溯到订单、方案、任务、记录及审核 |

## 二、默认健康规划师与订单归属

| 场景 | 状态 | 现状 | 差异 |
|---|---|---|---|
| 新注册客户自动绑定默认规划师 | 未实现 | 手机注册仅 `User.create({ phone })`；没有分配规划师 | 不满足“所有正式客户必须注册并绑定有效健康规划师” |
| 缺失归属的运行时兜底 | 部分具备 | `resolveHealthPlanner` 查首个 active 健康规划师 | 只返回 ID，不写回客户；“最早创建的 active 账号”不是明确的可配置默认账号；未兼容历史 `staffStatus` 为空 |
| 存量补配 | 未实现 | 未发现只补“空归属/已停用归属”的迁移或维护任务 | 不能保证存量完整性，也没有异常报告 |
| 商城自主下单 | 部分具备 | 普通订单经 `resolveOrderWorkflowAssignee`，一般归健康规划师 | 若无可用规划师，订单照常生成但不建待办，形成无责任人订单；解析出的默认人不持久化到用户 |
| 医务端推送后客户购买 | 部分具备 | `/user` 推送购买路径复用了同一 assignee resolver | 两入口原则基本一致；同样存在无规划师静默掉单 |
| 住院一站式 | 部分具备（有意例外） | 先归健康顾问做医学前置评估，之后就医方案由规划师执行 | 符合职责分阶段，但当前订单主任务本身改派给健康顾问，不是“订单始终归规划师 + 医学前置子任务归顾问”的主责/关联任务模型 |
| 服务咨询/续约 | 需修改 | 咨询仅在已有 `assignedHealthPlanner` 时建任务；续约仍优先健管专员 | 与统一由规划师承接的客户经营主线不一致；缺归属时会出现已登记但无人主责 |

建议建立唯一入口 `ensureAssignedHealthPlanner(user, reason)`：验证当前归属人员仍启用；为空或失效时按 Admin 明确配置的默认规划师补配并持久化；失败必须写入可见异常任务。注册完成、建档完成、两类下单、咨询/续约均调用同一入口。

## 三、三类方案端到端链路

### 1. 年度管理方案

状态：部分具备，但需优先重构审核与生效边界。

已具备：

- Admin `health_management` 模板可供 AI 生成使用。
- 健康顾问/超管角色限制已存在。
- `AnnualPlan` 保存结构化 `moduleData`、模板 ID/名称、推送与客户确认时间。
- 可同步周期随访、配药/营养素计划和治疗项。

主要差异：

- `AnnualPlan` 没有 `aiStatus`、审核人、审核时间、驳回原因等正式审核字段。
- 保存即生成随访、供应计划和治疗同步，审核/发布边界倒置。
- 仅保存 `templateId/templateName`，没有模板版本号和完整快照；Admin 后续修改模板时无法证明生成时依据。
- 年度方案结构字段仍是宽松 `Mixed`，缺少“是否需要→是否需协助→期限/地点/阶段周期”等强约束。
- 没有“复查后独立 AI 随访草稿”链路；现有月度/方案同步仍围绕年度方案本身。

目标链路应为：模板版本快照 → AI 草稿 → 健康顾问审核 → 发布 → 客户可见/确认 → 才创建正式任务与随访 → 完成后更新进程；复查后新计划独立保存，不回写年度方案。

### 2. 营养干预方案

状态：部分具备。

已具备：

- Admin 营养模板、营养师 AI 生成、`content.aiStatus=pending`、营养师待审入口。
- AI 草稿在客户端通过 `content.aiStatus != pending` 过滤；客户确认后生成随访。
- 模块化编辑与方案项目状态存在。

主要差异：

- AI 生成只保存模板 ID/名称，没有完整模板快照（就医方案已有局部快照，营养方案没有）。
- 前端“采纳”写入 `aiStatus=adopted`，但模型是 Mixed 且后端没有专门的方案审核 API、审核人/时间/意见；审核只是普通更新方案内容，审计性不足。
- 客户确认后生成的随访直接 `aiStatus=approved`，实际并未经历“复查后 AI 随访草稿→营养师审核”的二次闭环。
- 涉及诊断、药物或严重异常时的健康顾问会签未建模。
- 服务完成后的自动归档和全周期进程更新不完整。

### 3. 就医协助方案

状态：部分具备，三类中链路最接近目标。

已具备：

- Admin 模板、规划师 AI 生成、`content.aiStatus=pending`、规划师待审入口。
- 订单可关联 `sourceOrderId`；方案推送后建立执行随访，关闭原订单预约待办。
- 推送时预建“医院就医”服务记录底稿；随访完成后补写实际结果。
- 已保存局部 `templateSnapshot`，避免标准步骤随后被静默改变。

主要差异：

- 除住院一站式外，AI 提示仍允许“建议医院/科室/专家”，与“医学路径必须由健康顾问确定，规划师不得自行改变”冲突。
- 推送动作本身没有强制验证 `content.aiStatus` 已审核；普通更新接口可直接改状态，缺少专门审核审计。
- 模板快照仅含 tasks/hotel/transport/notes，缺版本号和完整内容快照。
- 推送时就先创建“医院就医”正式记录底稿；若“正式档案”必须在实际服务完成后形成，应改为执行草稿/进程事件，完成后再归档。
- “指定资源不可用→规划师反馈备选→顾问重新确认”的往返状态没有模型。
- 疑似专病资料的“待归档草稿→顾问审核→专病管理”未形成自动链路；“转介服务记录”分类也未发现完整自动归档。

## 四、AI 审核职责与安全边界

已具备：报告、档案问卷、汇总、生活方式、用药/营养素、风险、三类方案等大量待审数据源；多数待审内容已按角色和名下客户过滤，客户端部分接口也会过滤 `pending`。

需修改：

1. 将“待审核”从散落的 Mixed 字段约定提升为统一审计结构：`status`、`reviewRole`、`reviewerId`、`reviewedAt`、`reviewNote`、`sourceVersion`。
2. 所有发布/推送/入档/派单接口必须在后端强制检查审核完成，不能只依赖前端按钮隐藏。
3. 修正职责映射：最新口径中年度专项筛查、体检方案和年度管理方案归健康顾问；当前 `checkup_plan_review` 仍映射健管专员。
4. 把非医学自动化（固定提醒、状态同步、逾期升级）从“AI待审核”面板移出，避免误导；它们应属于工作台任务或督办。
5. 明确营养会签和就医医学路径确认的多角色状态机，不能用单一 `aiStatus` 表达。

## 五、尚未实现的两条核心自动化

1. 不适主诉安全分级与就医转介：现有不适主诉待核实/待处理及部分转介入口只能算基础；尚未形成固定危急安全提示、通知顾问/健管、明确挂号协助后转规划师、且规划师不参与医学分诊的完整状态链。
2. 复查结果审核后的独立 AI 随访：未发现“复查资料审核完成→AI独立随访草稿→健康顾问审核→进入现有随访→完成归档”的专用模型和端到端触发器。

## 六、建议实施批次

### P0：先修正确性和掉单风险

1. 修复首页简报 API 调用；后端一次返回 `today.pending/completed`、`month.pending/completed`、`overdue`。
2. `ensureAssignedHealthPlanner` 持久化默认归属，覆盖注册/建档/下单/咨询/续约；无可用规划师进入异常任务，禁止静默掉单。
3. 年度管理方案停止“保存即派单”，增加审核状态；仅审核并发布后同步正式任务。
4. 所有方案 push/confirm/入档入口增加服务端审核门禁。

### P1：统一工作台最小闭环

1. 建统一工作台聚合 API，不立即重构所有底层模型；把现有 FollowUp、AI todos、订单预约、逾期升级映射为统一 DTO。
2. 字段至少包含：任务类型、紧急度、截止时间、状态、主责任人、督办人、客户、来源对象、可执行动作。
3. 首页只展示一个可筛选列表；客户详情继续展示全周期进程。
4. 同一业务以 `sourceType + sourceId + taskKind` 去重；执行任务和督办任务分开。

### P2：三类方案标准化

1. Admin 模板引入不可变版本；三类方案保存完整版本快照。
2. 统一草稿/待审/已审/已发布/执行中/已归档状态与审核日志。
3. 按“是否需要”渐进展开年度结构字段；就医医学决策与执行安排分层。
4. 补齐服务完成归档、疑似专病审核归档、转介记录和全周期进程事件。

### P3：新增自动化

1. 不适主诉安全分级与转介。
2. 复查后独立 AI 随访计划。
3. 按健康顾问、健管专员、营养师、健康规划师逐角色做端到端验收。

## 七、首批验收用例

1. 健康顾问首页：我的有效会员准确；今日/本月均显示待与已；昨日及上月未完成任务持续出现在逾期区。
2. 新注册客户：自动绑定 Admin 配置的“嘉医管家”；停用该账号后新客户进入可见异常队列，不能生成无负责人订单任务。
3. 自主下单与推送购买：同一客户均归其既有规划师；来源人员只影响推广/绩效，不改变订单主责。
4. 年度方案 AI 草稿：待审期间客户端不可见、无 FollowUp/供应/治疗正式记录；顾问审核发布后一次性生成，重复发布不重复。
5. 营养方案：营养师审核前不可推送；涉及药物/严重异常时进入顾问会签；完成后归档“营养干预”。
6. 就医方案：医院/科室/专家必须来自顾问已确认字段；规划师只能补执行安排；资源不可用必须退回顾问确认。
7. 服务完成：自动归档“医院就医”；疑似专病只建待归档草稿，顾问审核后进入“专病管理”；全周期进程同步新增事件。
