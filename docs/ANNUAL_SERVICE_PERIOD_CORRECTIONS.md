# 续约更正：申请与审核阶段（2026-09-19，未部署）

> 后续已完成保留原排期的安全应用，见末节；前面的“待应用/尚未开放”描述保留为首阶段历史，不代表当前全部能力。

## 已确认业务

所属健康规划师更正合同/续约凭据，所属健康顾问审核受影响排期；保留原版本、冻结方案和已执行任务。沿用超管兜底权限，健管专员仅可查看，不参与重复确认。

## 本轮实现

- 原 `AnnualServicePeriod` 增加 `correctionRevision`、当前 `correction` 和追加式 `correctionHistory`。提交保存原凭据快照、拟更正凭据、原因、操作者和时间；不更新原生效字段或档案日期。
- 规划师提交后，顾问工作台出现一条“续约更正·顾问审核”；退回后转规划师。规划师可重新提交或撤回待审/退回申请。每个服务期同时只能有一条待审或待应用申请。
- 更正面板放在原年度方案续约凭据面板内，无新增客户操作；历史留痕可展开查看。
- 复用原年度凭据校验：已支付且未退款年度订单，或规划师明确核验的线下合同；年份、365/366天及有效日期规则保持原约束。检查与其他已确认年度重叠和重复订单。
- 影响快照包含冻结方案明确日期、现有客户任务、随访、周期补给的日期/状态/服务关联/停用信息，标识越界和须保留的记录。相对排期也提示需核对，不把此清单当成已计算完的安全迁移方案。
- 顾问审核前再次核对订单/重叠以及任务快照指纹；状态有变化时拒绝旧快照批准，顾问可刷新影响清单再核对。新增刷新审计，不抹掉提交时快照。
- 提交、审核、刷新和撤回通过同一文档版本条件原子写入当前状态及历史；过期版本/重复审核返回409，不静默覆盖。所属岗位和客户归属在服务端校验，审核接口不接受替换方案/凭据内容。

接口均在 `/api/staff/annual-plans/:planId/service-period` 下：

- `POST /corrections`：规划师提交。
- `POST /corrections/review`：顾问通过/退回。
- `POST /corrections/refresh-impact`：顾问刷新待审影响快照。
- `POST /corrections/withdraw`：规划师撤回待审/已退回申请。

均需 `expectedRevision`，后面三项还需匹配 `correctionId`。原GET返回当前更正及历史。

## 重要边界：不是已完成更正生效

审核通过只进入 `approved_pending_apply`，不替换生效凭据、不解冻年度方案、不调整或重开任务、不调用同步派发。页面明确显示“尚未生效/安全应用未开放”。此状态不创建需要人工重复点击的审核待办，面板保留可见状态。

原有效服务期及其既有调度继续运行；本轮不因申请更正而暂停客户服务。真正应用前必须重新检查有效凭据、相邻周期和当时任务状态，不能直接信任审核时快照。

下一步需实现：审核结果的持久应用队列、原凭据版本与有效版本的读取、稳定派单键/相对时间锚点保护、仅未执行且未关联任务的安全更正及异常补偿，确认过的历史执行与已启动服务绝不被覆盖。涉及新增或实质调整管理内容应仍走动态随访审核，不重复生成年度方案。尚未开放凭据撤销/退款结算、首次年度更正、跨年份方案迁移。

## 验证

347项相关回归通过，其中15项新增覆盖更正权限、提交/审核/撤回HTTP链路、日期与凭据校验、版本竞争、重复审核、影响快照变化、申请后退款、旧记录保留和工作台归属。员工端生产构建通过（原大包警告保留）。测试使用模拟数据库和本地HTTP，未连接真实AI/MongoDB或操作生产客户数据；尚未做浏览器多岗位端到端验收。

申请/审核阶段不更改现有运行链路，未部署；不能把本轮称为“更正已能自动生效”或完整闭环完成。

## 后续：保留原排期的安全应用（当前功能分支）

- 顾问在新审核页面明确选择保留原排期、安全条件满足后自动应用（`applicationPolicy: retain_schedule`）。旧页面缺该参数会拒绝审核；历史仅审核不应用的申请不能静默生效，需顾问重新核对。
- 审核持久化后立即尝试应用，不额外要求人工确认。`approved_pending_apply` 本身是持久待应用队列；既有每日窗口调度和原“重新核对并同步任务”入口重试，不新增定时器或AI调用。
- 应用时重验原凭据、订单支付/退款状态、相邻年度、冻结方案日期和当前任务。更换凭据与日期仅在保留排期仍安全时进行，绝不批量平移、取消、重开任务或改写年度方案。
- 越界方案日期、越界未执行任务、未进入30天窗口的相对排期、无明确日期服务需求默认起点越界均阻止应用。历史已完成、进行中、关联服务、人工停用记录保留不写；它们自身越界不直接当成应修改的任务，但方案对应固定日期越界仍需处理。
- 原执行起点保存到 `executionAnchor`，后续门槛仍至少不早于客户确认时间。更正合同开始日期不改变已有相对派单键，也不重设首次启用历史。应用不直接调用派单；之后沿用正常同步，未来期不提前启用。
- 当前生效凭据字段更新与 `correction.status=applied`、版本递增、原始/生效凭据审计在同一文档条件更新中完成。重复/并发应用只能成功一次，保留原规划师/顾问审核身份及历史快照。
- 正在登记同步的服务期暂不应用；新同步需匹配门槛读取时的更正版本，旧版本不能在更正后重新启动。该保护不是跨全部任务集合的事务或全局互斥锁。
- `evidenceOrderIds` 保留本服务期当前及历史订单，使用单字段 unique+sparse 多键索引；新订单确认及更正应用都检查实际索引已就绪。更换/改为线下合同不释放旧订单供其他年度再次使用；不回填历史数据，旧记录仍通过原 `sourceOrderId` 查询兼容。
- 应用受阻按原因进顾问（排期/审核变化）或规划师（凭据/数据库）工作台；相同异常每日重试不反复追加历史。暂时故障恢复可直接重试，不重新审核；内容需变化时规划师可重新提交、顾问可重新打开影响核对，也可撤回尚未生效的受阻申请。新内容仍须重新审核。
- 访问与监测解析器自然读取新的生效服务期；监测仍下一次既有扫描才刷新。不改客户档案日期、不新增客户任务。

验证：361项相关回归通过，员工端生产构建通过，原大包警告保留。新增覆盖原子应用、重复竞争、失败重试、旧审核不自动应用、执行起点稳定、历史订单保留/索引缺失、越界及未入窗口排期、退款和岗位待办；模拟数据库/本地HTTP，未进行生产写入或真实MongoDB验收。

上线前必须验证 `AnnualServicePeriod.evidenceOrderIds` 的真实 unique+sparse 索引，并配套发布员工端和后端，不能让旧版写入进程长期并行。跨文档“相邻服务期是否重叠”仍是读后检查，不是事务；订单退款与应用、独立随访同步/人工任务编辑与应用之间也没有全局原子性。完全数据库故障可能不能留异常，但待应用状态保留并由后续扫描恢复。

尚未实现：需要改变冻结方案本身/逐条移动越界任务的更正、跨年份迁移、合同撤销与退款结算、真实MongoDB并发及多岗位端到端验收。因此这是“保留原排期”的安全生效路径，不是所有更正场景均已闭环。未部署。
