# 嘉医汇统一业务营收与人员激励设计稿

日期：2026-11-12
状态：供业务验收的设计稿；本文件不代表功能已开发或已发布。

## 1. 最终目标与边界

超级管理员能从企业总览逐层查到产品、订单、客户、实际收退款、推广来源、服务交付、应付与已付激励、成本及规则依据。外部市场合伙人和内部健康顾问、营养师、健管专员等人员，均可按权限看到本人推广和服务业务。商城订单、线下合同、医护端登记共用一套订单和核算链。

一笔订单只能为企业贡献一次实际收款。推广归属、服务归属、佣金是不同视角，不能把各视角金额相加为企业营收。客户小程序只展示本人价格、付款和权益，不展示内部业绩、分摊或佣金。

## 2. 必须区分的四种金额

| 名称 | 计算与用途 | 是否直接相加到企业总额 |
| --- | --- | --- |
| 签约/订单金额 | 购买时的成交价，含未收款订单；用于销售漏斗 | 否 |
| 净实收 | 经核实的客户及第三方实际现金到账－成功现金退款；按收款日期展示现金经营视图 | 是，每笔支付或退款仅一次 |
| 已确认营业收入 | 按财务确认政策把已收款分配到相应服务期或交付节点；年度预收款不得在没有财务规则时直接称为当期已确认收入 | 是，但与净实收分开展示 |
| 业绩归属额 | 净实收在推广来源、服务模块等维度上的管理口径映射 | 否，是同一笔净实收的不同分析维度 |

第一版经营总览默认展示“净实收”，清楚标注是现金口径；“已确认营业收入”在财务确认规则和凭证接通前显示“待接入”，不得用净实收冒充。企业目标毛利率 50%～60% 作为可配置预警参考，非系统硬编码的佣金上限；未录入完整直接成本、交易费用及退款时不显示“实际毛利”。

金额统一以分存储与计算。付款、退款分别保留原始流水、发生时间、渠道、审核状态和订单关联；健康基金、赠送、优惠券等抵扣在支付构成中单列，不能重复作为新现金到账。企业代付等真实第三方到账须注明付款方、来源凭据和是否属于新的现金收入。

## 3. 一笔业务的统一身份和关系

每笔交易的最小追溯链为：机构 → 客户/服务对象 → 产品及规格 → 订单/合同 → 收退款流水 → 推广归属 → 子产品/岗位/实际服务人 → 履约证据 → 激励规则快照 → 计提/审核/发放/追回流水。

- 人员主档统一关联外部 `MarketPartner` 或内部 `Admin` 员工身份，保留其类型、岗位、机构与有效期。同一内部员工可在不同订单兼任推广人和服务人；每条贡献单独记录类型和证据。
- **推广来源**默认一笔订单一位主归属人：有效外部合伙人优先，否则有效内部员工，均无则记自然到店/其他来源。若以后允许联合推荐，须审批分成，推广归属百分比合计 100%，不能让两人各记 100% 的“合计业绩”。
- **成交协助**可另记内部促成人和转换贡献。外部合伙人带客、员工协助成交时，两个贡献可同时显示，但企业营收仍计一次；两种激励是否同时给付由产品规则决定并经成本校验。
- **服务归属**先拆解到子产品及负责团队，再落到实际执行员工。首页选择服务团队只是待执行人员安排，不自动认定其获得全部订单营收或服务激励。实际交付和验收后才生成个人服务业绩/激励。
- 一笔业务的“推广业务量”和“服务业务量”是两种指标；个人总览分栏显示，不合并成一个没有含义的“个人营收”。

现行归属规则沿用已有设计：外部市场合伙人通常只授权一个产品线；同一订单最多一位外部合伙人；有效推荐证据和规则在下单时冻结；跨产品须单笔授权。后续变更通过审批与差额记录，不覆盖原快照。

## 4. 产品与订单核算路径

| 产品类型 | 下单/收款 | 推广归属 | 服务归属与激励 |
| --- | --- | --- | --- |
| 单次就医 | 商城为主，线下可登记 | 首次或每次依已发布产品规则；历史重复购买按规则判定 | 实际就医协助节点验收后归属执行人 |
| 营养干预、体重/慢病管理 | 医护端按 Admin 产品库的商品及规格登记，财务核实线下收款 | 首次、续期及有效新客数依相应规则 | 营养师、健康顾问、健管专员按子服务或履约节点归属 |
| 365 与其他年度会员 | 365 可商城购买；其他会员按合同及服务期流程 | 以服务对象和产品线识别第 1～5 年及以后，沿用已定比例；线下续费须核对服务期 | 把组合服务拆到子产品，核算模块份额；实际交付单独计个人服务激励 |
| 检测、营养素补充 | 商城或医护端登记，物资仍走原履约流程 | 仅在该产品有已发布推广规则时计提 | 专业团队的推广、服务、交付分别凭证据核算 |

Admin 产品库是唯一的产品、规格、组合关系和标价来源。订单保存购买时规格、成交价、子产品拆解比例、岗位、个人覆盖规则等快照。组合子产品分摊比例须合计 100%；未配置时订单进入“待配置/待人工核算”清单，不虚构分摊。退款按各子项原比例冲减，分币尾差归最后一项。0 元权益核销履约单只增加服务记录，不能再增加企业收款或推广成交额。

年度预收款的**现金业绩**按实收月份统计；**服务期营业收入**按财务批准的确认规则另计。一次年度付款若分摊给健康顾问、营养师、就医团队，这只是同一笔净实收的内部模块归属；个人服务激励仍等实际履约达成。

## 5. 激励规则、状态与成本控制

规则层级：产品/规格/服务期 → 贡献类型（外部推广、内部推广、成交协助、服务）→ 岗位/具体人员覆盖 → 比例或固定额 → 触发与封顶 → 生效版本。无规则默认不计提；员工个人覆盖规则优先，但必须保留来源版本。既有外部合伙人首年、续年与部分单次产品比例保持原设计；规则由 Admin 维护，不在此稿中擅自改比例。

每笔激励分开显示：预计应计、已审核应付、实际已付、已追回、待追回。支付当天不发首笔；首笔与尾款按既定 7 天/30 天、正式流失、退款和月度阶梯规则核验。服务激励须有实际完成证据、岗位匹配及审核，不以收款或指定服务人自动发放。同一订单、人员、贡献类型、履约节点只能计提一次；外部和内部激励若并存，不能因两条系统记录重复认定同一贡献。

订单成本视图单列：履约直接成本、商品采购/物流成本、交易费用、外部推广费、内部推广费、服务激励、其他已核准变动费用。企业预计结余＝净实收－上述费用；这是管理测算，和财务已确认营业收入/利润区分。缺实际成本时标记覆盖率与待补项，不给出看似精确的实际毛利率。

## 6. Admin 信息架构与权限

### A. 运营管理 → 经营与分账总览（新增，超级管理员）

顶部固定显示所选期间：净实收、成功退款、已确认营业收入（未接入时显示待接入）、外部带来净实收、内部推广净实收、无推广归属净实收、预计激励、已付激励、成本覆盖率。每个指标可点击订单明细；推广来源三栏合计必须等于企业净实收。按付款日、产品、渠道、机构、合伙人/员工、业务类型筛选。

下方四张可切换明细表：**产品与渠道**、**推广来源**、**服务团队与个人**、**订单对账**。推广表按人展示有效客户数、首购/续费订单数、净实收归属、应计/已付推广费、退款；服务表按子产品/岗位/人员展示分摊业务额、已完成服务量、已审核/已付服务激励。每张表的总数必须能穿透到订单与流水；支持导出当前筛选结果及口径说明。

### B. 运营管理 → 市场合伙人（现有，配置与核对）

保留外部合伙人登记、授权产品线、推荐证据、规则版本、线下凭据、佣金审核和单笔订单核算。新增“查看经营总览中该合伙人的业务”跳转及合伙人列表的净实收归属、有效客户、应计/已付佣金列。现有“组合产品团队业务营收”只是团队视角，不能当作合伙人总营收。

### C. Admin 产品库（现有，规则源头）

在商品/规格详情统一呈现组合子产品、团队收入份额、岗位和个人推广/服务激励、触发节点、成本项、生效版本、试算结果。发布前校验份额 100%、角色/人员有效、激励不重复、必要成本齐全或明确待补。

### D. 员工与外部合伙人端

内部员工“我的业绩”分推广、服务、待确认、已审核、已发放；可穿透到自己有权限的订单和依据。外部合伙人现有只读查账入口增加相同的客户/订单/佣金口径，不展示其他人员、成本或客户医疗资料。客户小程序不展示这些内部金额。

管理端查询和导出均按机构隔离；超级管理员看全机构，财务角色看其被授权的收支与发放数据，普通员工和合伙人只看本人。查询敏感客户信息及导出留审计。

## 7. 数据账本与汇总实现

保留既有 `Order`、支付/退款、`MarketPartnerCommission`、`Commission`、`TeamIncentive`，新增统一的只读核算投影或事件账本，不另造一套可手改的订单金额。每条标准化记录带 `tenantId`、`orderId`、事件唯一键、来源流水号、金额分、发生时间、会计/经营期间、人员 ID、贡献类型、子产品 ID、规则版本和审核状态。

一笔支付或退款事件只能入账一次；重复回调、重复复核和重跑汇总须幂等。调整生成正负差额事件，原付款和已发放事实不可覆盖。汇总接口在数据库侧按完整筛选条件聚合与分页，不用前端最近 200 单相加。历史订单按证据逐批核对与迁移，缺推荐来源、收款凭据或产品拆解的旧订单列入“待归属/待核对”，不自动补造佣金。

每次刷新须通过的对账恒等式：

1. 企业净实收＝已核实现金收款－成功现金退款＝推广来源分组净实收合计（含“无归属”）。
2. 有完整组合拆解的订单，其子产品分摊净实收合计＝该订单净实收；未拆解订单单列，不导致企业总额缺失。
3. 外部合伙人、内部员工和团队服务各自的报表逐单合计＝相应激励账本计提/实付/追回金额；不同维度的业绩归属额不相加。
4. 收退款流水、订单净额、人员归属表和导出文件在相同筛选条件下金额一致；退款及归属更正均保留前后审计记录。

## 8. 需要覆盖的验收场景

| 场景 | 预期 |
| --- | --- |
| 外部合伙人带客，内部团队服务 | 企业净实收一次；外部推广业绩一份；实际执行人员按子项目出现服务业绩；激励分别计算 |
| 内部员工推广并亲自服务 | 推广和服务分别列示；同一贡献/节点不重复计提；企业总额一次 |
| 外部合伙人推荐，内部员工协助成交 | 来源与成交协助分别留痕；是否双重给付按产品规则；来源报表不双计 |
| 商城和线下同一产品 | 相同收款与归属口径；线下须经财务凭据复核才纳入净实收及佣金 |
| 年度会员首年、第二年、第三至五年、第六年 | 对应规则版本和年度序号；提前续费/中断/补款不错误重置序号 |
| 年度组合三团队拆分与部分退款 | 子项份额合计 100%；退款后企业及各子项金额同步减少；已发激励走追回流水 |
| 0 元权益核销 | 服务量增加；企业净实收和推广销售业绩不增加 |
| 未配置人员、成本或旧订单证据 | 进入待办清单；不伪造分配、毛利或佣金 |
| 重复支付/退款通知、跨机构查询 | 不重记账；跨机构不可见；导出同样隔离 |
| 大于 200 笔订单及多条件筛选 | 汇总不截断，分页明细与导出、总数一致 |

上线门槛是先完成真实数据库对账和合成全链路验收，再抽样核对线上真实历史订单；配置试点产品、人员及规则，先限定范围试点。代码、生产配置、Admin 页面、小程序和已发布 App 的相关入口分别核对版本与发布回执。设计验收通过只代表可以按此开发，不代表上述功能已经上线。

## 9. 与当前实现的差距

当前已有：订单上的收款/退款字段、外部合伙人与内部推广/服务人员关联、子产品拆解快照、员工个人绩效覆盖、外部佣金和团队激励、Admin 单笔订单核算及团队子产品营收汇总。

当前缺少：企业范围完整汇总、按合伙人和员工的统一业绩查询、全部订单而非 200 单的分页聚合、财务确认营收和真实成本接入、统一对账/待归属清单、完整的员工个人业绩视图。现有团队子产品汇总包含非合伙人订单，也不能代替合伙人业务总营收。设计不要求先填合伙人规则才能看企业净实收；规则只影响归属佣金与可分配的个人业绩。

## 10. 2026-11-12 首批实现记录

已在当前功能工作树增加超级管理员“经营与分账总览”入口和现金经营汇总接口。按订单 `paidAt` 筛选、按 `paidAmount - refundedAmount` 计算，包含全额退款订单、排除零现金权益履约单；数据库聚合全部符合条件的订单，分别给出外部合伙人、内部员工、无归属、产品和支付渠道视图。外部合伙人优先占用推广来源维度，内部员工协助成交尚未单独展示，因此不会在来源合计中双计。页面标注退款回溯原付款期，财务确认收入和线下真实流水对账尚未接入。

## 11. 可逐步操作的完整业务流程

| 阶段 | 操作人和入口 | 输入/审核 | 系统产物及阻断条件 |
| --- | --- | --- | --- |
| 1 产品建模 | 超管，Admin 产品库 | 商品或 365 服务包、规格、组合子项、收入权重 100%、岗位、服务节点、成本预算 | 发布产品版本；不完整组合进入待配置，不生成虚拟分摊 |
| 2 规则发布 | 超管，市场合伙人与员工规则 | 外部/内部推广、成交协助、服务激励、首年/续年、产品与个人覆盖、封顶和生效期；另一管理员复核关键金额 | 冻结规则版本；发布前以样例试算；不能凭岗位名称自动给付 |
| 3 人员与来源 | 运营，合伙人和客户入口；医护端 | 合伙人授权产品线、合同、推荐码/链接或员工推荐证据、服务对象 | 客户来源事件；推荐到下单时须重新验证，有冲突进入归属审核 |
| 4 创建业务 | 客户商城或医护端登记 | 客户、商品规格、成交价、外部合同号或自动业务编号、推荐来源、预定服务人员 | 唯一订单号、当时产品/规则快照；登记者和预定服务人不自动成为推广人或完成人 |
| 5 收款 | 微信回调；线下财务复核 | 微信成功支付流水；线下真实到账金额、流水、凭证与双人复核 | 现金收款事件；未到账、未复核或凭证不一致的线下单不能计正式现金业绩或佣金 |
| 6 推广计提 | 系统自动，异常由运营审核 | 有效归属、产品授权、首次/续费序号、到账、退款和流失记录 | 外部/内部推广预估；来源归属额与激励分开；7/30 天门槛及阶梯尾款 |
| 7 服务履约 | 医护端具体人员 | 子项目、实际执行人、次数、完成节点、验收证据 | 模块业务归属、个人已交付服务量及服务激励；未履约只显示预分配 |
| 8 发放与冲回 | 财务及另一复核人 | 应付清单、实付流水、退款或正式终止依据 | 已付、待付、待追回和实际追回；只追加差额流水，不修改历史打款事实 |
| 9 对账与关账 | 超管/财务，总览 | 企业总数、来源、产品、人员、订单、收退款与导出核对 | 差异为零后标记期间已核对；缺凭据、无归属、旧单拆解缺失形成待办 |

支付后即使尚未指定最终服务人员，也应在企业净实收和推广来源中出现；服务人员页面只显示待分配或待履约。退款成功后立即更新现金视图，待审退款不提前扣减。产品或人员规则改版不倒改历史订单。线下多次到账或分期付款应记录逐笔收款事件，订单实收为其合计；跨期退款在“资金发生日”视图记退款当日，在“付款期回溯净额”视图冲原付款期，两种视图清晰标注并可对账。

## 12. 页面级验收蓝图

超级管理员从 **运营管理 → 经营与分账总览** 进入，第一屏显示期间、口径开关（资金发生日/付款期回溯）、企业净实收、推广来源三栏、退款、待核对金额、数据最后刷新时间。点击任何数字进入预设筛选的订单列表；列表每行展示订单号、客户、产品/规格、渠道、收退款、外部来源、内部推广/促成、服务团队、激励状态。点击行进入“订单一页核算”，可打开原收款、退款、合同、推荐、履约和审批依据。订单金额和人员归属均支持导出，导出文件保留筛选条件、生成者、生成时间及口径版本。

第二屏按 **合伙人/员工** 切换。每位人员固定分为推广业务（有效客户、首购、续费、净实收归属、佣金）与服务业务（负责子项、完成次数、分摊额、服务激励）；同一人可同时出现两栏，但顶部企业总额不能加两次。外部合伙人只见自己的推广栏；内部员工可见本人推广及服务栏。下钻客户时仅展示有权限的业务摘要，外部合伙人不得看到医疗档案。

第三屏按 **产品/组合子项** 切换。展示总产品净实收、子项权重与金额、负责团队、实际履约量、岗位和个人服务激励、成本覆盖与留存；未拆解和未指定人员的金额独立列为待办，不能消失在总额之外。财务已确认收入在规则接通前显示“待接入”，不显示 0 元误导。

Admin **市场合伙人** 页面保留配置和审批，不再充当经营总账。Admin **产品库** 是商品/规格、组合和激励的配置入口。医护端是客户业务登记、实际人员和服务节点的事实入口。客户小程序只看自己的购买与权益。

## 18. 本轮真实数据库流程结果

找回既有已校验的本机 MongoDB 7.0.34 可执行文件后，使用随机隔离库运行 `backend/test/marketPartnerFlow.integration.test.js`。真实 HTTP/JWT/Mongo 流程覆盖线上/线下合成付款、365/年度续费、组合拆解、服务团队完成和退款、企业汇总及跨机构隔离、规则草稿修改和新旧版本接续、合伙人资料修改留痕。2026-11-12 最新执行通过；Admin 生产构建通过。所有订单和客户都是隔离库合成数据，不触碰生产。端到端页面操作、实际微信交易、财务收入与成本、个人业绩总览仍待实现与验收。

同日继续：经营与分账总览新增按来源分页的订单明细，逐笔可跳至同单核算；团队视角按相同付款期间显示已配置 100% 拆解的组合订单，含退款后的分摊额。未拆解订单依旧留在企业净实收，不被团队表遗漏成“企业无收入”。真实隔离 HTTP/Mongo 测试新增分页、来源筛选与跨机构明细隔离；通过。Admin 构建通过。当前仍不能把预定服务人员等同于实际服务个人业绩，也不能把团队分摊额称为已经发放的服务费。

专项核对发现：现有 `TeamIncentive` 计提和退款重算仍使用整笔订单净现金作为 `basisCents`。组合子产品虽然已能按权重拆分团队营收，但团队专项激励还没有逐子项的履约证据和分摊基数；多个岗位直接按整单比例配置会算高。组合产品在“子项实际完成/核销 → 对应人员 → 子项净实收份额 → 该子项规则 → 激励”链路改完并通过退款回归前，不应启用这类专项激励规则。现有单项服务团队激励流程可按原规则继续验收。该风险属于上线阻断，不能用总览团队表掩盖。

## 19. 组合子项专项激励实现与复核

上述阻断点已在本地候选代码中继续修正：组合母产品不能发布整单专项激励；应按各子产品建立岗位规则。组合订单提交计提时必须选择购买时快照里的子项、对应岗位、该子项真实核销记录和实际人员；金额基数是子项净实收份额再按购买时包含次数分到本次核销，分币尾差归最后一个子项/最后一次核销。审核时再次核对子项核销证据；退款后重算该子项本次基数和应计，超付进入原有追回流程。普通单项服务仍沿用已完成履约记录和整单净现金基数。

隔离 MongoDB/JWT/HTTP 用例覆盖：组合母产品整单规则被拒绝、缺子项核销拒绝、两类子产品按 60%/40% 分摊的单人激励、双人审核、追加退款后的各子项重算；纯金额测试覆盖同一子项多次核销。2026-11-12 该组合流程与既有线上/线下、续费、退款、规则修改测试一并通过（4 项测试、0 失败）；Admin 构建通过。此处仅为隔离合成订单和页面构建，未在实际医护操作中对同一核销记录指定执行人，也未部署生产。

补充唯一约束：同一订单、岗位、服务触发和核销证据只允许一位实际人员计提，不能改用另一员工 ID 重复领取。隔离库已创建新唯一索引并验证第二人认领返回 409；生产启用前必须只读核对现存重复证据、显式迁移索引，再打开对应规则。更正实际执行人应走审批和差额流水，不能直接改旧激励记录；该纠错入口仍待开发。

## 20. 管理服务与实物/检测产品分开归属（用户修订）

年度健康管理等套餐是独立定价的持续服务，不能把售价解释为关联商城单品标价之和。当前线上“组合服务子项目”要求每项都关联产品库子产品；这只适合明确打包出售的单项商品，不适合纯管理服务或同时包含管理服务和检测、营养素的套餐。此限制须改造，不能为了凑满 100% 而创建虚构商品。

Admin 在可售套餐（商城产品或年度会员服务包）编辑中维护一份版本化的**订单净现金归属方案**，每行选择“管理服务”或“产品/检测”：

| 行类型 | 配置与证据 | 归属和激励 |
| --- | --- | --- |
| 管理服务 | 自定义服务模块名称、负责岗位、管理周期或实际完成节点、可选负责人；不强制关联商城产品 | 从整单净实收按配置权重分配模块金额；岗位业务营收按模块归属，个人服务激励只在实际履约及规则命中后产生 |
| 产品/检测 | 必须关联真实产品库项目或规格、交付数量、领用/检测/发货凭据；可指定负责团队 | 从同一笔净实收按配置权重分配产品业务金额；库存、实际采购和检测成本另记，不能用单品标价替代套餐分摊价 |

两类的权重合计 100%，基数是**套餐订单核实的现金净实收**，退款按订单购买时冻结的拆解版本重算，最后一行承担分币尾差。权重只是内部业务归属口径，不是拆分销售价格、财务收入确认、个人佣金比例或实付金额。合伙人推广费按母套餐适用规则和净现金另算；同一笔现金在企业总额中仅出现一次。直接成本、平台费用、推广费、服务费各列为支出，不从某个团队的营收份额里偷偷抵减。

例如套餐实收 10,000 元，可由 Admin 分配管理服务 8,000 元、检测/营养产品 2,000 元；管理服务再分配顾问、营养师、健管岗位。假设关联单品的商城标价总和是 6,000 元，也不改变这笔订单的 10,000 元现金或上述分配。最终实际人员、已完成服务量和奖金仍依履约证据及独立激励规则产生。

修改入口应在 Admin 产品库或年度会员服务包的编辑页，以“服务归属”和“产品/检测归属”分别编辑并预览合计；保存时校验两类合计 100%、产品引用真实且同机构、服务模块有明确岗位。新订单冻结配置快照；历史订单保持旧版，若要纠正走审批与差额记录。经营总览分别展示服务模块和产品/检测归属，另列未拆解金额待办；逐单核算可追溯母套餐实收、每行归属、履约、成本和激励。此节为待实施修订，当前线上尚未具备“管理服务不关联子产品”的配置和核算能力。

## 21. Admin 直接设置服务团队归属金额（用户进一步明确）

以下金额仅为用户解释分摊方法的假设案例，不对应任何实际产品、售价或已配置规则：若某套餐的配置基准价为 5,000 元，Admin 可以填“健康顾问管理 3,000 元、健管专员跟进 2,000 元”，无须关联子产品。界面据此生成 60%/40% 归属比例；若该订单实际成交 5,000 元，团队业务归属才是 3,000/2,000 元。订单优惠或成功退款后按冻结比例同比缩放，企业实收仍只记一笔。实际产品的价格及归属金额均由管理员逐项设置；不同收费规格若需不同绝对金额，后续须配置规格级归属版本。

服务模块的团队业务归属与实际人员服务费分离：只有服务核销、实际人员和生效岗位规则均核实后，才按该模块的净实收份额计专项激励。确有独立商品或检测交付时，产品库子产品关联仍可选用；关联商品沿用其自己的激励规则。当前实施范围是商城产品的服务团队归属；年度会员服务包和产品/检测收入类别的独立报表仍待接入，不能称为已完成。
